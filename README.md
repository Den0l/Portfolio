Это статический сайт-портфолио: у него нет сервера, базы данных, API загрузки
файлов и админки. Сайт собирается из файлов в `public/` и изображений в
каталоге `projects/`.

## Требования

- Node.js версии 20 или новее (npm устанавливается вместе с Node.js).
- Репозиторий GitHub и включённый GitHub Pages для публикации.

Дополнительные npm-пакеты устанавливать не нужно.

## Добавление и изменение проектов

1. Создайте в `projects/` отдельную папку для каждого проекта, например
   `projects/Outfits/`.
2. Поместите изображения проекта в эту папку. Сборщик также находит картинки
   во вложенных папках.
3. Выполните сборку командой `npm run build`.

Название папки используется как название карточки: дефисы и подчёркивания
заменяются пробелами, слова отображаются с заглавной буквы. Поддерживаются
форматы `.avif`, `.gif`, `.jpeg`, `.jpg`, `.png` и `.webp`. В именах папок и
файлов разрешены пробелы и символы других языков. Фотографии сортируются по
пути в естественном алфавитном порядке: например, `photo-2` будет перед
`photo-10`.

Слайдер заполняется изображениями из всех папок проектов. Пример структуры и
подробности — в [projects/README.md](./projects/README.md).

## Настройка профиля

Измените [`public/site-config.json`](./public/site-config.json):

- `siteTitle` — заголовок сайта и имя в шапке профиля.
- `description` — текст под фотографией профиля.
- `profileImage` — путь к фотографии профиля. Локальное изображение поместите в
  `public/images/` и укажите относительный путь, например
  `./images/profile.jpg`.
- `socials` — список ссылок с полями `label` (название) и `url` (адрес).

В адресах соцсетей указывайте схему, например `https://`. Следите, чтобы файл
оставался корректным JSON: строки заключаются в двойные кавычки, между
элементами ставятся запятые.

## Сборка и локальный просмотр

Выполните из корневой папки проекта:

```sh
npm run build
```

Сборка создаёт `dist/`: готовую страницу, манифест проектов и копии
изображений. Это генерируемый каталог — редактируйте исходники в `public/` и
`projects/`, а затем запускайте сборку заново.

Для локального просмотра раздавайте именно `dist/` по HTTP. Если открыть
`index.html` напрямую, браузер не загрузит JSON-файлы сайта.

Windows (если установлен Python):

```powershell
py -m http.server 8000 --directory dist
```

macOS или Linux:

```sh
python3 -m http.server 8000 --directory dist
```

Откройте <http://localhost:8000>. Чтобы остановить локальный сервер, нажмите
`Ctrl+C`.

## Публикация в GitHub Pages

В репозитории уже есть workflow
[`.github/workflows/deploy.yml`](./.github/workflows/deploy.yml). Он запускает
`npm run build`, загружает каталог `dist/` и публикует его через GitHub Pages.
Собирать сайт вручную на GitHub или добавлять `dist/` в репозиторий не нужно.

### Первая публикация

1. Создайте репозиторий на GitHub. Если сайт должен быть доступен всем, выберите
   **Public**. Для GitHub Pages из приватного репозитория могут применяться
   ограничения плана аккаунта или организации. Если код уже находится локально,
   создайте пустой репозиторий без добавления README, `.gitignore` и лицензии.
2. Откройте терминал в корневой папке проекта. Назначьте ветку `main` и добавьте
   адрес созданного GitHub-репозитория как `origin`:

   ```sh
   git branch -M main
   git remote add origin https://github.com/ВАШЕ_ИМЯ/ИМЯ_РЕПОЗИТОРИЯ.git
   ```

   Замените адрес на URL своего репозитория с GitHub. Если `origin` уже
   существует, вместо `git remote add` используйте
   `git remote set-url origin https://github.com/ВАШЕ_ИМЯ/ИМЯ_РЕПОЗИТОРИЯ.git`.
3. Проверьте файлы и отправьте ветку:

   ```sh
   git status
   git add .
   git commit -m "Prepare portfolio for GitHub Pages"
   git push -u origin main
   ```

   Если `git commit` ответит, что коммитить нечего, это нормально — пропустите
   эту команду и выполните `git push -u origin main`.

   Убедитесь, что в репозиторий попали папки `public/`, `projects/`,
   `scripts/`, `.github/workflows/` и файлы `package.json` и `README.md`.
   `dist/`, `node_modules/`, `.env` и старый каталог `data/` отправлять не
   требуется: они исключены через `.gitignore`.
4. На GitHub откройте репозиторий → **Settings → Pages**.
5. В разделе **Build and deployment** установите **Source** в
   **GitHub Actions**.
6. Откройте вкладку **Actions**. Workflow **Deploy static site to GitHub
   Pages** должен автоматически запуститься после `push`. Если он не запустился,
   выберите workflow и нажмите **Run workflow**.
7. Дождитесь зелёного статуса у обеих задач — `build` и `deploy`. Адрес
   опубликованной страницы появится в журнале задачи `deploy`, а также на
   странице **Settings → Pages**. Первый деплой может занять несколько минут.

Для обычного проектного репозитория URL чаще всего имеет вид
`https://<владелец>.github.io/<имя-репозитория>/`. Используйте точный URL,
показанный GitHub: он может отличаться при использовании собственного домена
или сайта аккаунта.

### Обновление сайта

Измените файлы в `public/` или изображения в `projects/`, затем отправьте
изменения в отслеживаемую ветку:

```sh
git add .
git commit -m "Update portfolio"
git push origin main
```

Workflow сам пересоберёт сайт и опубликует новую версию. Локальный `npm run
build` нужен для предпросмотра, но готовый каталог `dist/` коммитить не надо.

### Если основная ветка не `main`

Сейчас workflow реагирует на отправку изменений в `main` и на ручной запуск.
Если ваша основная ветка называется, например, `master`, измените в файле
workflow:

```yaml
push:
  branches: [master]
```

После этого отправьте изменение workflow в GitHub. Альтернативно можно каждый
раз запускать публикацию вручную через **Actions → Deploy static site to
GitHub Pages → Run workflow**.

### Доступность опубликованного сайта

При публичной публикации сайт и все входящие в сборку фотографии доступны
посетителям по ссылке, даже если исходный репозиторий закрытый. Приватный
репозиторий сам по себе не включает авторизацию на сайте. Приватный доступ к
Pages доступен только в поддерживаемых конфигурациях GitHub Enterprise.
Не публикуйте в `public/` или `projects/` пароли, личные фотографии и другие
конфиденциальные данные.

## Если что-то не работает

- **На странице ошибка загрузки данных:** заново выполните `npm run build` и
  раздавайте `dist/`, а не `public/`.
- **Проект не появился:** проверьте, что его папка находится непосредственно
  в `projects/` и содержит изображение поддерживаемого формата.
- **После изменения сайт не обновился:** проверьте результат последнего
  workflow во вкладке **Actions** и обновите страницу после успешного деплоя.
- **Workflow не запускается после отправки изменений:** проверьте имя ветки
  в `push.branches` файла workflow и убедитесь, что в **Settings → Pages**
  источником выбрано **GitHub Actions**.
- **Workflow сообщает об ошибке прав:** проверьте, что Actions разрешены для
  репозитория или организации. Workflow использует права `Pages: write` и
  `id-token: write` для публикации.
- **В задаче `deploy` ошибка `Failed to create deployment (status: 404)` или
  `Ensure GitHub Pages has been enabled`:** откройте репозиторий на GitHub →
  **Settings → Pages**, выберите источник **GitHub Actions** и сохраните
  настройку. Затем повторно запустите workflow во вкладке **Actions**. Если
  раздел Pages недоступен, проверьте, разрешён ли GitHub Pages для репозитория
  и поддерживает ли ваш план Pages для репозитория этой видимости.
- **Страница открылась, но картинки не загрузились:** проверьте, что изображения
  добавлены в `projects/` и отправлены в GitHub, а последний запуск workflow
  завершился успешно. Не используйте локальные абсолютные пути вроде
  `C:\...`.

## Старые локальные данные

Если в копии проекта осталась папка `data/` от прежней серверной версии, она
не используется сайтом, не копируется в `dist/` и исключена из Git. Папка
оставлена локально как архив — перед её удалением проверьте её содержимое.
